# Shaar HaYichud: Study Guide (demo)

A proof-of-concept study guide for chapters 1–5 and 10 of the Mitteler Rebbe's
*Shaar HaYichud*, built to discuss with Markel Son. For each passage the site
shows the Hebrew text, Rabbi Amiram Markel's English translation (from
Sefaria) and an explanation drafted from Rabbi Markel's recorded classes,
with buttons that play the moment in the class where the passage is
explained. It is a static Astro site, and it prints as a booklet.

**Draft, not reviewed.** The explanations were drafted by AI from the class
recordings and have not been reviewed by Rabbi Markel. The site says so on
every page, is set to `noindex` and disallows crawlers in `robots.txt`.
Do not distribute it.

The design is in [`docs/spec.md`](docs/spec.md).

## Layout

```
package.json  tsconfig.json  astro.config.ts  .node-version
scripts/
  vendor.ts            # builds data/ from shaar-hayichud-sections and Sefaria
  validate-content.ts  # checks content/ against data/ (runs before every build)
  build-pdf.ts         # prints /book/ to the KDP PDF (npm run pdf)
  dump-chapter.ts      # prints a chapter's text and transcripts, for writers
  review-notes.ts      # lists every reviewer note
  test-typography.ts   # checks src/lib/typography.ts (runs in npm run check)
data/                  # generated by vendor.ts and committed; never edit by hand
  sources.json         # the classes: titles, audio URLs, durations, outlines
  chapters/            # per chapter: segments (Hebrew lines, English, footnotes, coverage)
  transcripts/         # per chapter: each line's transcript span, tape preambles
  raw/sefaria/         # Sefaria API responses, cached
  ATTRIBUTION.md       # sources, commit and licences of everything in data/
content/               # the guide itself, hand-editable Markdown and YAML
  STYLE.md             # how explanations are written: read before editing
  translit.yaml        # one spelling for each transliterated term
  chapter_NN/          # _chapter.md, _terms.yaml, NN-concept.md files
src/
  lib/schema.ts        # Zod schemas of data/ (the contract between script and site)
  lib/chapters.ts      # the chapters in the booklet, shared by the scripts and the site
  lib/content.ts       # loads data/ and content/ into typed chapter models
  layouts/ components/ pages/ styles/ scripts/
public/                # robots.txt, favicon
```

Pages: `/` (cover and contents), `/chapter/N/` for each chapter (1–5 and 10),
`/booklet/` (all chapters on one page, for printing), `/glossary/`, `/about/`,
and `/book/`, the source of the print-ready PDF (see below; not linked from the
site's navigation).

## Running it

Node 22 (see `.node-version`).

```sh
npm install
npm run dev        # local server with live reload
npm run build      # validate content, then build the static site into dist/
npm run preview    # serve dist/
npm run check      # astro check (types) + content validation
npm run pdf        # build, then the print-ready PDF in pdf/ (see below)
```

## Re-vendoring the data

`data/` comes from two places, and `scripts/vendor.ts` rebuilds it:

- [yringler/shaar-hayichud-sections](https://github.com/yringler/shaar-hayichud-sections):
  the Hebrew text with line IDs, the class catalog, Sofer.ai transcripts and
  outlines, re-timed word times and line alignments.
- Sefaria's API for "The Gate of Unity": the English translation, and the
  Hebrew used only to decide which Sefaria paragraph each line belongs to.

```sh
# with the sections repo checked out at ../yringler/shaar-hayichud-sections
npm run vendor
# or name the checkout, and refetch Sefaria instead of using data/raw/sefaria/
npx tsx scripts/vendor.ts --sections <path> --refetch-sefaria
```

The script writes the same bytes for the same inputs, checks its output
against `src/lib/schema.ts`, and fails if the line-to-paragraph mapping is
inconsistent. It records the sections commit in `data/sources.json` and
`data/ATTRIBUTION.md`. Commit `data/` afterwards, then run `npm run validate`:
content written against the old data may need its listen links or segment
ranges updated. The classes it reads are constants at the top of the
script; the chapters are listed in `src/lib/chapters.ts` (shared with the
validator and the site). Chapter files are named
`chapter_NN` with two digits (`chapter_05`, `chapter_10`). Class 001, the
series introduction, has no aligned lines; the script vendors its whole
transcript as chapter 10's first preamble (`INTRODUCES` in the script).

## Editing the content

Each chapter is a folder under `content/`:

- `_chapter.md`: title, status, `## Overview` and `## Review questions`.
- `_terms.yaml`: the chapter's key terms.
- `NN-slug.md`: one file per concept, in order. Its frontmatter holds the
  heading, the segment range, the "In short" text, a status
  (`ai-draft`, `no-source`, `edited`, `reviewed`) and any reviewer notes. The
  body has one `## §n` (or `## §n–m`) section per unit, with the explanation.

`content/STYLE.md` has the full rules: voice, bold quotes from the
translation, transliterations, listen links (`[▶ 4:12](listen:021#252)`, class
`021` at second 252) and callouts. A few practical points:

- Use the spellings in `content/translit.yaml`. Add a new term there (or to
  the chapter's `_terms.yaml`) instead of inventing a second spelling.
- When an explanation has been checked, change the concept's `status` from
  `ai-draft` to `edited` or `reviewed`.
- `npm run dump -- 3` prints chapter 3's text and class transcripts side by
  side, with the seconds for listen links.
- `npm run validate` checks everything (`-- --chapter 3` for one chapter).
  Errors fail the build: concepts or units that leave a gap or overlap, a
  listen link to an unknown class or a time past its end, a unit with no
  listen link, a term spelled against `translit.yaml`, bad frontmatter, "God"
  instead of "G-d". Warnings point at things worth a look: a listen link far
  from where the passage is read (often a deliberate recap citation), a bold
  phrase that is not a verbatim quote, Hebrew script left in the prose.
- Type plain ASCII quotes and apostrophes, and ' or " for a Hebrew geresh or
  gershayim (כו', חב"ד). Rendering (`src/lib/typography.ts`, for the site and
  the book) turns them into “ ” ‘ ’, ׳ and ״, keeps each class reference
  "(class 18, 22:26)" on the line with the word before it, and starts an
  explanation paragraph that opens on a lower-case bold quote with "…". The
  files themselves are not changed, so the validator checks them as typed.

## Review notes

Wherever the drafter left something out, was unsure what was said, or made
a judgement call, it is recorded in the `reviewNotes` list in that concept's
frontmatter, each entry starting with the `§` it concerns:

```yaml
reviewNotes:
  - "§27: the transcript's 'עד דסלק' is ע״ב דס״ג misheard."
```

On the site these appear in a dashed "For the reviewer" box at the foot of
the concept (screen only, never printed). To list them all:

```sh
npm run review-notes        # every chapter, grouped by concept, with statuses
npm run review-notes -- 1   # chapter 1 only
```

Resolve a note by fixing the text and deleting the entry. A unit left empty
on purpose must have a note naming its `§`; the validator enforces this.

## Print-ready PDF for KDP

`npm run pdf` makes the paperback interior for Amazon Kindle Direct Publishing:
trim 7 × 10 in, no bleed, black and white, fonts embedded. It builds the site,
serves `dist/` locally, opens `/book/` in Playwright's Chromium and prints it
to `pdf/shaar-hayichud-booklet-1-7x10.pdf` (`pdf/` is not committed).

```sh
npm run pdf                              # Study guide view, draft notices on
npm run pdf -- --view explanation        # guide | explanation | text
npm run pdf -- --final                   # without the draft notices
npm run pdf -- --no-build --out x.pdf    # reuse dist/, write elsewhere
```

- **The book:** title page, copyright and credits page, contents with page
  numbers (chapters and concept headings), "About this guide", the chapters,
  and the glossary with page references. Each chapter starts on a right-hand
  page; running heads (book title on the left, chapter on the right) and page
  numbers on the outside corners; none on the title and copyright pages.
  Transcripts, class topic lists, reviewer notes, audio and navigation are
  never printed.
- **Design** (`src/styles/book.css`): a 5.3 × 8.2 in text block (margins top
  0.85, outside 0.8, bottom 0.95, inside 0.9 in), body 11 pt with oldstyle
  figures, black ink only (KDP prints greys as halftone), hairline rules. Each
  passage sets the translation and the Hebrew in two open columns without a
  frame; the Hebrew is ragged, the English prose justified with hyphenation
  limits and `text-wrap: pretty`. Labels are Source Serif small caps. Chapter
  openers are sunk and centred and have no running head (the opener has its
  own named page, `kopener`, as Chromium has no `:first` for named pages); the
  key terms start the following page.
- **Page numbers:** the front matter (title, copyright, contents, "About this
  guide" and a blank page if needed so that chapter 1 is a right-hand page) is
  numbered in roman, counted from the title page (i, ii, iii, …; the title
  and copyright pages print none), and chapter 1's first page is 1. The
  contents and glossary page references use the same numbers, and the script
  writes them into the PDF as `/PageLabels`, so a PDF viewer's page box shows
  them too. Chromium's page counter cannot be restarted, so `book.css` counts
  the arabic folios with a counter of its own (`folio`), which the
  front-matter pages do not advance.
- **Fonts:** Source Serif 4 and Frank Ruhl Libre (SIL OFL) set the book;
  Source Sans 3 (SIL OFL) is vendored and declared too, though the book no
  longer uses it. They are vendored with their licences in
  `public/fonts/print/` and declared in `src/styles/book.css`, so printing
  needs no network. They keep every
  OpenType feature (real small caps, oldstyle and tabular figures, Hebrew mark
  positioning), which the `@fontsource` subsets lack. They are static
  instances because Chromium embeds variable fonts as Type 3: Source Serif 4
  at optical size 12 for text, and `Source Serif 4 Display` at optical size 36
  for large headings. `scripts/make-print-fonts.py` (Python with fontTools and
  brotli) downloads and rebuilds them: Source Serif 4 and Frank Ruhl Libre
  from google/fonts, instanced and subset to Latin, Hebrew and punctuation;
  Source Sans 3 is Adobe's static TTF, unmodified because its licence reserves
  the name "Source". The italic and the Hebrew have no small caps.
- **Draft notice:** by default the title page, copyright page and the foot of
  every page say the book is a draft. `--final` removes them, and first prints
  a warning listing every section whose status is not `edited` or `reviewed`.
  A copyright line (and ISBN, if any) goes in `COPYRIGHT_LINE` in
  `src/pages/book.astro`.
- **Checks:** the script fails if content runs into the margins, a font
  does not load, a chapter starts on a left-hand page, a page is not
  504 × 720 pt, a font is not embedded or is a system fallback (`pdffonts`),
  any page has colour (`pdftoppm`), or the printed folios do not match the
  page labels (`pdftotext`). It pads to an even page count and warns
  under KDP's 24-page minimum. The summary gives the page count and the gutter
  used against KDP's minimum for that count (0.9 in by default, above KDP's
  minimum for any page count; the script would widen it itself if not).
  `pdffonts`, `pdftoppm` and `pdftotext` are in poppler-utils; without them
  those checks are skipped with a warning.
- **Chromium:** Playwright 1.63.0 (`npx playwright install chromium` once, if
  it is not installed). Chromium neither inserts blank pages for
  `break-before: right` nor supports `target-counter()`, so the script prints
  in passes: it reads each heading's page from the PDF, adds blank pages and
  fills in the page numbers, and prints again until nothing changes.
- **Without a local setup:** the "Build and deploy" GitHub Actions workflow
  (`.github/workflows/deploy.yml`) builds the PDF on every push to `main` and
  on demand (Actions → Build and deploy → Run workflow, choosing the view,
  whether it is final, and whether to deploy). The PDF is attached to the run
  as an artifact and published with the site (see below).

Uploading to KDP (Paperback → Paperback Content): Print options **Black & white
interior** on **cream or white paper**, trim size **7 × 10 in**, bleed
**No bleed**; upload the PDF as the manuscript and check it in the Print
Previewer. The cover is separate and is not produced here (its spine width
depends on the final page count and paper).

## Deploying to Cloudflare Pages

The site is plain static files (no functions or adapters), but the book PDF
needs Chromium, which Cloudflare's Git-connected build does not have. So
GitHub Actions builds and deploys: `.github/workflows/deploy.yml` runs
`npm run pdf` (content validation, the site build, then the PDF), copies the
PDF into `dist/` and runs `wrangler pages deploy`. A push to `main` deploys to
production; running the workflow by hand on another branch makes a preview.
The PDF is served at `/shaar-hayichud-booklet-1-7x10.pdf` (linked from the
cover and `/booklet/`), with an `X-Robots-Tag: noindex` header from
`public/_headers`.

One-time setup:

1. In Cloudflare, the Pages project `shaarhayichudstudydemo` (production
   branch `main`). If it is connected to Git, turn off automatic production
   and preview deployments (Settings → Builds & deployments), or both
   Cloudflare and the workflow will deploy.
2. A Cloudflare API token with **Account → Cloudflare Pages → Edit**.
3. Repository secrets (Settings → Secrets and variables → Actions):
   `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

To deploy by hand instead:

```sh
npm run pdf
cp pdf/shaar-hayichud-booklet-1-7x10.pdf dist/
npx wrangler pages deploy dist --project-name shaarhayichudstudydemo
```

The build runs the content validator first, so a content error fails the
deploy rather than publishing a broken page. The site is `noindex`; consider
Cloudflare Access to keep it private (open question 10).

## Open questions

None of these blocks the demo; they are for the discussion with Markel Son.

1. **Whose translation is on Sefaria?** It is credited to Rabbi Amiram Markel
   (CC-BY, neirot.com). Is that the cousin's translation Markel Son meant, or
   is there another one he would rather use? CC-BY allows reuse with credit;
   the demo credits it and links to Sefaria.
2. **Hebrew text rights.** Sefaria lists the Hebrew version's licence as
   "unknown" (source: neirot.com). The demo uses the Hebrew already held in
   shaar-hayichud-sections. Fine for a private demo; needs a clear answer
   before booklets are distributed.
3. **Transliteration style.** The guide uses Ashkenazi/Chabad spellings
   (*chachma*, *hisbonenus*) per Markel Son's example, while the translation
   uses *Chochmah*/*Hitbonenut*. Leave the mismatch, respell the translation
   (CC-BY permits changes, marked as such), or have him supply a spelling
   list? (`content/translit.yaml` is the current list.)
4. **Chapter 1's first 20 paragraphs have no recording** in this series, nor
   do chapter 10 §48–64 (between tapes 003 and 004) and §82–84 (not read in
   class). Does Rabbi Markel have another shiur on these passages? More generally: which
   other shiurim exist, in what form, and may they be transcribed? The content
   format already lets one passage cite several classes; future work is a
   teacher/series field per source in the UI, a policy for when two classes
   explain a line differently, and transcription cost (Sofer.ai per audio
   hour).
5. **Voice.** Should the explanation speak impersonally (as drafted) or
   attribute to "Rabbi Markel" throughout? Should students' questions from
   the recordings appear?
6. **Publishing the recordings and raw transcripts** with the guide: is
   Rabbi Markel comfortable with listen links and the "source transcript"
   panel in what students see, or should those be for reviewers only?
7. **Review workflow.** How do he and his father want to edit: Markdown files
   in GitHub, a Google Doc export, or comments on a printed draft? This decides
   whether a simple editing UI is worth building.
8. **Pace and packaging.** A one-year course, a weekly two-hour shiur, 54
   chapters: how many chapters per week and per booklet? Print size (Letter
   or an A5 booklet)? Does Lemaan Yilmedu have a house style, or need its name
   on the cover?
9. **Depth.** The classes are an "advanced" series with long digressions.
   How much belongs in a preparation guide: only what explains the line, or
   also the wider discussions (for example chapter 5's two extra tapes)?
10. **Privacy and indexing.** The demo is set to `noindex` on a public
    pages.dev URL. Should it sit behind Cloudflare Access instead?
